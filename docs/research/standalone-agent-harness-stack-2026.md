# Standalone agent-harness stack for SHALLOT (2026-08-26)

**Status:** Research recommendation  
**Scope:** Standalone, Python-first agent outside Zed; official documentation, repositories, specifications, and releases only.  
**Repository inputs:** [`cub/pyproject.toml`](../../cub/pyproject.toml), [ADR 0005](../adr/0005-cub-agent-stack.md), [ADR 0006](../adr/0006-cub-agent-inference-architecture.md), [ADR 0007](../adr/0007-oss-integration-stack.md).

## Decision

Use this stack:

1. **Harness/runtime:** **Pydantic AI 2.34.x** plus a **pinned Pydantic AI Harness 0.24.x**, using ordinary Pydantic AI agents and only the harness capabilities SHALLOT needs. Use `pydantic-graph` for explicit deterministic state machines, not as the persistence database. Pydantic AI now officially supports MCP, evals, durable-execution adapters, deferred/HITL tool calls, broad model providers, and a separate harness with filesystem confinement, repo context, memory notebooks, planning, subagents, and context compaction. The harness is explicitly 0.x and may change between minor releases, so hide it behind a small SHALLOT-owned composition module and pin exact versions. [Pydantic AI v2.34.0](https://github.com/pydantic/pydantic-ai/releases/tag/v2.34.0) · [Harness overview](https://pydantic.dev/docs/ai/harness/) · [Harness v0.24.0](https://github.com/pydantic/pydantic-ai-harness/releases/tag/v0.24.0) · [pydantic-graph persistence](https://ai.pydantic.dev/api/pydantic_graph/persistence/)
2. **Operational state and memory source of truth:** **PostgreSQL + pgvector**, with explicit SHALLOT tables for runs, events, approvals, provenance, memories, document chunks, source revisions, and sync cursors. PostgreSQL supplies ACID transactions, joins, backup/PITR, access controls, and audit-friendly relational state; pgvector adds exact/approximate vector search (HNSW/IVFFlat, dense/sparse vectors) without another authoritative database. [pgvector](https://github.com/pgvector/pgvector)
3. **Memory model:** implement three explicit, reviewable stores over PostgreSQL rather than outsourcing semantics to a black-box “memory” product:
   - **episodic:** immutable run/tool/HITL events plus compacted summaries, linked to GitHub issue and trace IDs;
   - **semantic:** versioned facts with provenance, confidence, validity interval, supersession, and embeddings;
   - **procedural:** version-controlled Markdown runbooks/skills in the repository, indexed for retrieval but changed only through reviewed GitHub work. Pydantic Harness `Memory` may serve as a bounded agent notebook, not the canonical memory database. Its official implementation is filesystem-backed Markdown with bounded search and optimistic writes. [Harness memory](https://pydantic.dev/docs/ai/harness/memory/)
4. **Repository/docs RAG:** ingest Git blobs and selected Craft documents into PostgreSQL/pgvector. Store `source_uri`, Git SHA or Craft block/document revision, chunk hash, ACL/sensitivity, and deletion tombstone. Combine PostgreSQL full-text search with vector similarity and reranking. Add **Qdrant** only if retrieval scale or sparse+dense hybrid quality demonstrably outgrows Postgres; Qdrant has mature hybrid search, payload filters, multitenancy, snapshots, and audit access logging, but creates a second operational datastore. [Qdrant hybrid search](https://qdrant.tech/documentation/search/text-search/hybrid-search/) · [multitenancy](https://qdrant.tech/documentation/manage-data/multitenancy/) · [v1.17 audit logging](https://github.com/qdrant/qdrant/releases/tag/v1.17.0) · [v1.19.0](https://github.com/qdrant/qdrant/releases/tag/v1.19.0)
5. **Models:** local Ollama/OpenAI-compatible inference by default; cloud models behind the ADR 0006 deterministic policy gate. Pydantic AI is model-agnostic and the harness composes over it. Do not let the model select the provider/tier. Validate each local model’s structured-output and tool-call behavior; “provider-compatible” does not imply equal agent reliability.
6. **Tools/integration:** MCP at the boundary, not as the internal domain model. Use the official GitHub MCP server with only required `repos`/`issues` tools and least-privilege credentials. Connect Craft through its scoped MCP endpoint; default it to read-only. MCP HTTP authorization is optional at protocol level, so enforce OAuth/audience binding, token storage, server allowlists, timeouts, output limits, and per-tool policy in the harness. [Pydantic MCP client](https://pydantic.dev/docs/ai/mcp/client/) · [GitHub MCP toolsets](https://docs.github.com/en/copilot/how-tos/provide-context/use-mcp-in-your-ide/configure-toolsets) · [Craft MCP](https://support.craft.do/en/integrate/mcp) · [Craft MCP security](https://support.craft.do/en/integrate/mcp/security) · [MCP 2026-07-28 authorization](https://modelcontextprotocol.io/specification/2026-07-28/basic/authorization) · [security considerations](https://modelcontextprotocol.io/specification/2026-07-28/basic/authorization/security-considerations)
7. **Canonical work tracking:** GitHub Issues remains canonical. Craft is an operational mirror for human visibility. Mirror GitHub→Craft asynchronously with idempotency keys and a stored cursor. A Craft-originated edit must become a proposed GitHub mutation, require policy/HITL where consequential, commit to GitHub first, then reflect back to Craft. Never resolve conflicts by last-write-wins across both systems.
8. **Observability/evals:** instrument with **OpenTelemetry/OpenInference-compatible spans** and place an **OTel Collector** between the app and backend. Start with **self-hosted Phoenix** for the thesis/lab because it is active, local, evaluation-oriented, and lighter than the full Langfuse production topology; keep backend choice replaceable. Keep eval datasets and deterministic security assertions in Git. Phoenix v20.4.0 includes retrieval relevance evaluation and an MCP toolset. [Phoenix v20.4.0](https://github.com/Arize-ai/phoenix/releases/tag/arize-phoenix-v20.4.0) · [OpenTelemetry semantic conventions](https://opentelemetry.io/docs/concepts/semantic-conventions/)
9. **Durability:** begin with Postgres-backed run/checkpoint state and idempotent tools. Add **Temporal** when runs must survive process/host restarts, wait days for approval, enforce durable timers, or coordinate non-idempotent side effects. Pydantic AI has a native Temporal capability; Temporal’s Python SDK is mature and its HITL pattern uses durable Signals and preserves an audit trail. Do not deploy Temporal merely for chat continuity. [Pydantic AI durable execution](https://pydantic.dev/docs/ai/capabilities/durable_execution/overview/) · [Temporal integration](https://pydantic.dev/docs/ai/capabilities/durable_execution/temporal/) · [Temporal HITL](https://docs.temporal.io/ai/cookbook/human-in-the-loop-python) · [Python SDK 1.32.0](https://github.com/temporalio/sdk-python/releases)
10. **Security:** run tools in rootless Podman with a read-only base, explicit writable workspace, dropped capabilities, no inherited host secrets, egress allowlist, per-tool deadlines/output budgets, append-only provenance, and approval for writes/destructive operations. Pydantic Harness filesystem guards contain paths and symlinks, but they are application controls—not a kernel sandbox. [Harness filesystem](https://pydantic.dev/docs/ai/harness/filesystem/) · [Harness shell](https://pydantic.dev/docs/ai/harness/shell/)

## Why this is the best balance

This choice preserves the project’s Pydantic investment and type safety while removing two weak points in the current design: opaque memory semantics and backend-coupled telemetry. PostgreSQL is already sufficient for canonical long-lived state, provenance, RAG metadata, and modest vector search. The agent framework stays replaceable because GitHub, Craft, storage, model routing, tools, and telemetry are outside its private abstractions.

The main risk is **Pydantic AI Harness maturity**: its current release is 0.24.0 and its documentation explicitly warns that minor releases may change APIs. Mitigation: pin, wrap capability construction, persist only SHALLOT-owned schemas, and maintain a small framework contract test suite. Pydantic AI itself is on 2.34.0 and has a much more mature core release line. [Harness version policy](https://pydantic.dev/docs/ai/harness/) · [Pydantic AI releases](https://github.com/pydantic/pydantic-ai/releases)

## Observability and evals

- **OpenTelemetry:** mandatory portability layer. Emit run, model, retrieval, memory, policy, MCP, tool, approval, GitHub-sync and Craft-sync spans; redact content by default and attach hashes/IDs instead. Semantic conventions standardize names but do not define SHALLOT’s audit policy. [OTel conventions](https://opentelemetry.io/docs/concepts/semantic-conventions/)
- **Phoenix:** recommended initial backend. Active OSS release cadence, tracing/experiments/evals and retrieval evaluation; easy local thesis deployment. Keep security/audit records in Postgres/Wazuh, not only in an observability UI. [Phoenix releases](https://github.com/Arize-ai/phoenix/releases)
- **Langfuse:** strongest self-hosted collaborative LLM engineering alternative: tracing, datasets, prompt management, online/offline evaluation and OTel SDKs. v4.19.0 is current, but production self-hosting adds ClickHouse-class operational weight; low-scale Docker Compose lacks HA/backups. [self-hosting](https://langfuse.com/self-hosting) · [OTel SDK](https://langfuse.com/docs/observability/sdk/overview) · [v4.19.0](https://github.com/langfuse/langfuse/releases/tag/v4.19.0)
- **Logfire:** best Pydantic AI developer experience and integrates Pydantic Evals, application traces and SQL-like analysis, but it is primarily a hosted service rather than the local-first system of record. Use optionally during development; never make it the only audit sink. [Logfire evals](https://logfire.pydantic.dev/docs/guides/web-ui/evals/) · [integrations](https://logfire.pydantic.dev/docs/integrations/)
- **LangSmith:** mature LangGraph-native tracing/evals and supports OTel. Self-hosting is an Enterprise-plan add-on and deploys several services, so it conflicts with the desired standalone/local-first balance unless LangGraph is selected and budget supports it. [self-hosting](https://docs.langchain.com/langsmith/self-hosted) · [OTel](https://docs.langchain.com/langsmith/trace-with-opentelemetry)
- **Latitude:** the existing dependency remains active and now uses OTel, but ADR 0007’s uncited “better than Logfire” decision is not reproducible. Prefer direct OTel and select a backend through measured SHALLOT eval/operations criteria. [Latitude Python telemetry](https://docs.latitude.so/telemetry/python) · [official repository](https://github.com/latitude-dev/latitude-llm)

## Required evaluation gates

Before enabling autonomous writes, create a versioned corpus of SHALLOT cases and require:

- issue selection/triage accuracy and no unauthorized issue mutation;
- repository RAG citation precision/recall, stale-revision rejection, and deletion propagation;
- episodic/semantic/procedural write classification and provenance completeness;
- prompt-injection resistance from GitHub issue bodies, Craft blocks, logs and retrieved documents;
- deterministic denial of cloud routing for sensitive inputs;
- exact HITL behavior for write/destructive tools, including restart/resume;
- tool idempotency, retry safety and duplicate Craft/GitHub event handling;
- secret/PII absence from prompts, traces and memory stores;
- local-model tool-call conformance and cloud/local quality deltas.

## Existing ADR/package claim audit

| Existing claim | 2026-08-26 status |
|---|---|
| ADR 0005: Pydantic AI requires “own small flow control” because it lacks a finished graph/runtime. | **Stale.** Pydantic AI now has an official Harness, `pydantic-graph`, deferred tools, evals and four official durable-execution integrations. The minimalist decision can remain, but the rationale must be updated. |
| ADR 0005: swap Ollama/cloud models “without code changes.” | **Overstated.** Provider selection is portable, but tool calling, structured output, native tools, usage reporting and reasoning metadata differ. Provider contract tests and explicit capability profiles are required. |
| ADR 0007: Supermemory is “one binary, zero config,” mature enough to replace local memory, and covers episodic + semantic + procedural memory. | **Unsupported/unsafe as stated.** Current self-hosting is a binary and can run locally, but requires an extraction LLM configuration; the server is 0.0.8 and just repaired silent vector loss during upgrade. Official docs describe graph memories/RAG, not a verified three-type contract matching ADR 0006. |
| ADR 0007: Supermemory “95% Recall@15” proves it wins. | **Unsupported decision evidence.** This is a vendor-published benchmark claim. No SHALLOT corpus, reproducible configuration, security test, migration test or independent primary project evidence is cited. |
| ADR 0007: Supermemory TTL/purge implements GDPR minimization. | **Unsupported.** No retention/deletion verification, tombstone behavior, backup deletion, or audit procedure is specified in the ADR. A product feature cannot establish compliance without tested lifecycle controls. |
| ADR 0007: Latitude is self-hosted and categorically “better LLM tracing” than Logfire. | **Unsupported comparative claim.** Latitude is active and OTel-based, but the ADR has no criteria or measurements. Direct OTel avoids backend lock-in; Phoenix/Langfuse/Logfire should be selected by deployment, eval and data-residency needs. |
| `cub/pyproject.toml`: broad lower bounds (`pydantic-ai>=1.0`, `supermemory>=0.1`, `latitude-telemetry>=0.1`). | **Operationally unsafe.** Current major/minor lines have changed substantially. Use a lockfile and compatible upper/exact pins, especially for Pydantic AI Harness, telemetry SDKs and any memory engine. |
| ADR 0007: Hanko can serve as the FIDO CTAP backend and wrap a hardware driver. | **Unsupported architecture claim.** A WebAuthn relying-party server and a USB CTAP device driver are different trust boundaries/protocol roles. Keep RP integration separate from FIDO Key transport/firmware tooling unless an official Hanko capability explicitly proves this path. |
| ADR 0006: encrypted/scrubbed persistent memory plus provenance gives safe long-term memory. | **Incomplete.** Add source-level ACLs, tenant/project namespace enforcement, deletion propagation, retention, backup handling, embedding leakage analysis, retrieval authorization, poisoning defenses and approval for procedural-memory mutation. |

## Implementation order

1. Replace framework-specific state with SHALLOT-owned Postgres schemas and an append-only provenance/event model.
2. Pin Pydantic AI; add pinned Harness only for `RepoContext`, bounded `FileSystem`/`Shell`, planning/compaction and optional notebook memory.
3. Implement GitHub Issues canonical adapter and read-only Craft mirror adapter; add idempotent outbox/inbox records.
4. Build repository/docs ingestion with revision-aware Postgres full-text + pgvector retrieval.
5. Add OTel Collector and Phoenix; commit eval datasets and security assertions.
6. Add Podman execution and policy/HITL gates before any write-capable MCP/tool exposure.
7. Introduce Temporal only when restart-safe long waits or multi-step side effects are demonstrated; otherwise retain the simpler Postgres checkpoint path.
8. Benchmark Qdrant, Graphiti, Mem0 or Supermemory only against the committed SHALLOT eval corpus. Promote none to canonical storage.
